# 포항시의회 날짜 연도 검증 누락

## 발생 내용

초기 포항시의회 의안 크롤러는 `YYYY-MM-DD` 형식과 달력상 존재 여부만 확인했다. 이 때문에 원문 상세 페이지에 입력된 `0207-06-27`, `0200-07-07` 같은 연도 전치 오타도 유효한 ISO 날짜로 통과했다.

전체 3,112건 생성 후 날짜 최솟값을 검사하는 과정에서 문제를 발견했다. 총 11개 상세 날짜가 이 패턴에 해당했다.

## 원인

문자열 형식 검증과 `Date` 왕복 검증은 4자리 연도가 업무적으로 타당한 범위인지 보장하지 않는다. JavaScript는 서기 0200년 같은 값도 정상 날짜로 처리한다.

## 수정

- 포항시의회 데이터가 가질 수 있는 연도를 1990년부터 수집 시점의 다음 연도까지로 제한했다.
- 원문의 `02xx-MM-DD` 패턴은 알려진 연도 전치 형태로만 `20xx-MM-DD`로
  정규화하고, 보정 결과가 수집 시점 기준 허용 범위와 실제 달력 날짜를 모두
  통과할 때만 채택했다. 다른 필드나 인접 레코드에서 날짜를 추론하지 않는다.
- 보정 전 값, 보정 후 값, 대상 필드, `source_year_transposition` 코드를 상세
  JSON, 정규화 CSV, PostgreSQL `council_record.metadata.dataQualityIssues`에 보존했다.
- 범위 밖이면서 안전하게 보정할 수 없는 값은 `null`로 격리하고 `invalid_source_date` 이슈로 남기도록 했다.
- `0000-00-00`은 `missing_date_sentinel`, 점 구분 날짜는 `source_date_delimiter_normalized`로 구별해 원문 품질 문제를 한 종류로 뭉개지 않았다.
- 회귀 테스트와 전체 데이터 날짜 범위 검사를 추가했다.

## 재발 방지

형식이 맞는 날짜도 업무상 허용 범위, 전체 데이터의 최솟값·최댓값, 원문 보정 이력을 함께 검사한다.
