# 측정 공개와 이식성: 벤치마크 대시보드, 광역시도 어댑터

## 1. 벤치마크 대시보드 (`4e976c8`)

### 문제

정확도에 대한 주장이 README 안에만 존재하면 그것은 근거가 아니다. 이 프로젝트는
"검증 가능한 근거만 행정 행동으로 컴파일한다"고 말하면서, 정작 자기 자신의
성능에 대해서는 검증 가능한 형태를 제공하지 않고 있었다.

### 구현

- `GET /api/benchmark` — `evals/reports/*.json`을 읽어 반환한다.
- `apps/web` 하단에 통과율, 지표별 통과율, p95/중앙값 응답시간, 수작업 대비
  절감 시간을 표시하는 패널을 추가했다.
- `evals/reports/heuristic.json`, `llm.json`을 커밋해 화면에 데이터가 있게 했다.

### 결정: 대시보드는 측정을 실행할 수 없다

엔드포인트는 `pnpm benchmark`가 남긴 보고서를 **읽기만** 한다. 화면이 자기
측정을 트리거할 수 있다면, 데모는 질문받은 그 순간에 필요한 숫자를 만들어 낼 수
있게 된다. 그것은 이 프로젝트가 반대하는 바로 그 구조다.

부수적인 두 결정:

- 보고서는 부팅 시 캐시하지 않고 요청마다 읽는다. 서버가 떠 있는 동안 실행한
  벤치마크가 재시작 없이 보이도록 하기 위해서다.
- 보고서가 없거나 깨졌으면 500이 아니라 빈 목록을 반환한다. **없는 측정은 없어
  보여야지 고장 나 보이면 안 된다.**

현재 값(운영 PostgreSQL):

| planner | 통과 | p95 | 수작업 대비 절감 |
| --- | --- | --- | --- |
| heuristic (postgres) | 15/15 | 2.74s | 383분 → 382.8분 절감 |
| llm:gpt-4o-mini (postgres) | 15/15 | — | — |

## 2. 광역시도 지역 어댑터 (`569ca50`)

### 문제

"경북에서 검증한 뒤 다른 지자체로 이식 가능하다"는 주장을 가로막는 마지막
지점이 지역 정규화였다. 규칙 자체(정확 일치 → 부분 포함 → 해당 도의 의회 명칭)는
경북에 특화된 적이 없었고, **경북에 특화된 것은 이름 목록뿐**이었다.

### 구현

`pipelines/src/region-adapter.ts`

- `ProvinceRegionConfig` — 도 코드, 명칭, 약칭, 시군 목록, 폐지 명칭
- `createRegionAdapter(config)` → `{ regions, resolve, infer, byId }`
- 별칭(청 / 의회 / 시의회 / 군의회)은 **나열하지 않고 파생한다.** 손으로 별칭을
  써 줘야 하는 명칭은 우리가 그 명명 규칙을 아직 이해하지 못한 명칭이다.
- `regions.ts`는 경북 바인딩만 남긴 얇은 파사드가 되었다(외부 API 동일).
- `csv.ts`의 인구 정규화 함수들이 어댑터를 **인자**로 받는다(기본값 경북).

### 결정: 전라남도는 데이터가 아니라 테스트로 싣는다

두 번째 도 설정을 넣은 목적은 데이터 확대가 아니라 **경북 코드를 반증하는
것**이다. 경북 이름 덕분에 우연히 동작하던 규칙이 있다면 전남에서 즉시 깨진다.
같은 정규화 함수에 전남 파일을 통과시키는 테스트가 이식성을 문장이 아니라
실행으로 증명한다.

### 결정: 잘못된 도로 읽은 파일은 0건이 된다

`군위군`(2023년 대구광역시로 편입)은 경북 어댑터에서 절대 해석되지 않고, 전남
파일을 경북 어댑터로 읽으면 행이 나오지 않는다. 한쪽 도의 수치를 다른 도에
조용히 귀속시키는 이식성은 이식성이 없는 것보다 나쁘다.
