# 자기가 쓴 저장본을 되읽어 자기 상태를 덮었다

## 증상

`/chat`에서 후속 질문을 보내면, 요청이 시작되자마자 답변 자리가
**"답변을 가져오지 못했습니다 / 요청이 중단되었습니다"** 로 바뀌었다.

이상한 점이 두 가지 있었다.

1. 서버는 멀쩡히 응답하고 있었다. 네트워크 탭에서 SSE가 계속 흘렀다.
2. `/ask`에서 넘어온 **첫 질문은 정상**이었다. `/chat` 안에서 보낸 후속
   질문만 깨졌다.

## 원인

`prototype/src/lib/conversations.ts`의 저장 경로가 자기 자신에게 알림을
보내고 있었다.

```
send()
  → persist(next)
      → setConversations(next)        // 화면 상태: 대기 중인 턴이 들어간다
      → writeConversations(next)
          → localStorage.setItem(...) // 저장본: 대기 중인 턴을 error로 굳힌다
          → dispatchEvent(EVENT)      // ← 자기 창에 알린다
              → subscribeConversations 리스너
                  → setConversations(readConversations())
                      // 방금 만든 대기 턴이 error로 덮인다
```

`writeConversations`가 진행 중인 턴을 실패로 굳혀 저장하는 것 자체는
의도된 동작이다. 저장본에 `pending`이 남으면 새로고침한 뒤에 아무도 돌리지
않는 스피너가 영원히 돈다. **저장 시점의 처리로서는 옳다.**

잘못된 것은 그 저장본을 **쓴 사람이 곧바로 되읽은 것**이다. 저장본의
"실패"는 "이 세션은 끝났다"는 뜻이지 "지금 이 요청이 실패했다"는 뜻이
아닌데, 되읽는 순간 그 구분이 사라진다.

`/ask`에서 온 첫 질문이 무사했던 이유도 여기서 나온다. 그 경로는
`patch(mutate, save=false)`라 저장을 건너뛰고, 따라서 알림도 나가지 않는다.
이 비대칭이 버그의 표면이었다 — 같은 화면에서 같은 모양의 요청이 출처에
따라 다르게 동작했다.

## 고친 방법

`writeConversations`에서 자기 창 `dispatchEvent`를 제거했다.

- **같은 탭**은 이미 호출부가 새 상태를 들고 있다. 알릴 필요가 없다.
- **다른 탭**은 브라우저의 네이티브 `storage` 이벤트로 알게 된다. 이 이벤트는
  값을 쓴 탭에서는 울리지 않으므로, 구조적으로 자기 write를 되읽을 수 없다.

같은 탭의 다른 화면이 명시적으로 알려야 할 일이 생기면 쓰라고
`notifyConversations()`를 따로 남겨 뒀다. 저장과 알림을 한 함수에 묶어 두는
한 이 실수는 언제든 되살아난다.

`subscribeConversations`에는 `storage` 리스너가 이미 붙어 있었으나 키를
가리지 않아 다른 앱의 저장 변경에도 반응했다. `event.key`를 검사하도록
좁혔다.

## 회귀 테스트

`prototype/src/lib/conversations.test.ts` 5건.

- 저장본에서만 진행 중인 턴을 실패로 굳힌다 (호출자가 넘긴 배열은 그대로)
- **저장이 구독자를 깨우지 않는다** ← 이 버그를 고정하는 테스트
- 다른 탭의 변경(`storage`)은 구독자에게 전달한다
- 관계없는 키의 저장 변경은 무시한다
- 새 대화(`startConversation`)는 진행 중 상태 그대로 저장한다

마지막 항목이 중요하다. `/ask`에서 만든 대화는 도착한 `/chat` 화면이 그
`pending` 턴을 보고 요청을 시작한다. 여기까지 실패로 굳히면 아무 요청도
일어나지 않는다. 저장본을 굳히는 규칙과 굳히지 않는 규칙이 왜 갈리는지를
테스트로 남겨 뒀다.

## 남는 교훈

**저장은 상태 변경이 아니다.** 저장 함수가 "무언가 바뀌었다"고 방송하면,
그 방송을 듣는 쪽에서는 저장본이 곧 진실이 된다. 저장본은 다음 세션을 위해
가공된 것이지 지금의 진실이 아닐 수 있다 — 여기서는 정확히 그 가공(진행
중 → 실패)이 지금의 진실을 파괴했다.

쓰기와 알림을 한 함수에 묶으면 이 구분이 눈에 보이지 않는다. 분리해 두면
호출부가 "지금 알려야 하나?"를 매번 마주하게 된다.
