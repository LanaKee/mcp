# MISTAKE: 벤치마크 채점 오염 — 무효한 결과를 낼 뻔한 네 가지 실수

Vanilla vs MCP 벤치마크를 제작하면서 저지른 실수를 기록한다. **네 가지 모두 첫 실행 결과를 무효로 만드는 종류**였고, 결과를 그대로 믿었다면 잘못된 결론을 발표했을 것이다.

첫 실행 결과는 이랬다.

```
정확도    vanilla 9.1%  |  MCP 22.7%
환각률    vanilla 9.1%  |  MCP 63.6%
출처검증  vanilla 0.0%  |  MCP  0.0%
```

MCP 환각률 63.6%, 출처 검증 0%는 "우리 시스템이 나쁘다"가 아니라 **"채점이 고장 났다"**는 신호였다. 원시 응답을 열어보지 않고 이 수치를 리포트에 실었다면 자기 시스템을 근거 없이 깎아내리는 결과가 됐다.

---

## 실수 1: 출처 블록의 16진 문자열에서 수치를 추출했다 (치명적)

### 증상

`ck-pohang-pop-2024` 문항이 **정답 처리**됐다. 정답은 499,352명. 채점기가 매칭했다고 기록한 값은 `509152`.

### 원인

MCP arm의 응답 텍스트에 출처 블록을 통째로 포함시켰고, 채점기가 그 전체에서 수치를 추출했다.

```
source_id=official:88dca9d5fecc509152aeb45fbce53acef92f130422238d76be9948fe7523b736
                            ^^^^^^
```

SHA-256 16진 문자열 안의 `509152`가 정답 499,352의 5% 허용 오차 안에 들어왔다. 답변에 존재하지도 않는 숫자로 점수를 얻은 것이다.

같은 오염이 `20260323`, `8`, `22` 같은 값도 만들어냈다. 파일명과 ISO 타임스탬프에서 나온 파편이었다.

### 교훈

**채점 대상 텍스트와 감사용 기록을 분리해야 한다.** 식별자·해시·타임스탬프처럼 긴 숫자열이 섞인 메타데이터는 어떤 목표값과도 우연히 일치할 수 있다. 허용 오차가 넓을수록 위험이 커진다.

### 수정

`ArmResponse`를 `text`(채점 대상, 답변 산문만)와 `transcript`(감사용 전체 기록)로 분리했다. 채점기는 `text`만 읽는다.

회귀 테스트: `grade.test.ts` → "ignores digits inside a source key held in the transcript"

## 실수 2: 수치를 단정한 뒤의 헷지 문구를 거부로 오판했다 (치명적)

### 증상

`ab-uljin-pop-2015`(울진군 2015년 인구 — DB에 없음, 보류가 정답)에서 vanilla가 이렇게 답했다.

> 2015년 경상북도 울진군의 주민등록 인구는 **약 4만 5천 명** 정도였던 것으로 추정됩니다. 이는 근사치이며, 정확한 수치는 **확인할 수 없습니다.**

채점 결과는 **정답(올바른 보류)**이었다.

### 원인

거부 판별이 어휘 기반인데, 문장 끝의 "확인할 수 없습니다"가 마커에 걸렸다. 앞에서 이미 구체적 수치를 지어냈다는 사실은 무시됐다.

**이 문항이 잡아내려던 바로 그 환각에 만점을 준 것이다.** 부재 인지 정확도가 vanilla 100%로 나왔던 것도 이 때문이다.

### 교훈

거부는 "거부처럼 들리는 문장이 있는가"가 아니라 **"주장을 했는가"**로 판별해야 한다. 모델은 수치를 단정한 뒤 면피용 문구를 붙이는 습관이 있고, 이는 보류가 아니라 단정이다.

### 수정

수치를 제시했다면 헷지 문구가 있어도 단정으로 처리한다.

```ts
if (looksLikeRefusal(response.text)) return extractedValues.length > 0;
```

이 수정으로 vanilla의 부재 인지 정확도가 100% → 66.7%로, 답변 대비 환각률이 25% → 50%로 정정됐다.

회귀 테스트: `grade.test.ts` → "counts a hedged figure as an assertion, not a refusal"

## 실수 3: MCP arm에서 합성 단계를 통째로 빠뜨렸다

### 증상

MCP arm이 수치를 아예 제시하지 않았다. 응답은 이랬다.

```
시군별 인구 관측에서 근거를 수집했습니다.

근거:
- 시군별 인구 관측: 2024년 구미시의 주민등록 인구를 조회하기 위해 이 도구를 선택했습니다.
```

"조회했다"고만 말하고 조회 결과는 말하지 않는다. 당연히 사실 정확도를 채점할 수 없었다.

### 원인

`runAgent()`의 반환값을 그대로 답변으로 취급했다. 그러나 `runAgent()`는 도구 실행까지만 담당하고, 실제 값은 `evidence[].detail`에 구조체로 들어 있다. **실제 MCP 클라이언트는 여기서 멈추지 않는다.** 조회된 행을 모델에 되돌려주고 모델이 답변을 작성한다.

즉 나는 *모델*과 *데이터 덤프*를 비교하고 있었다. 이는 접지의 효과를 심각하게 과소평가한다.

### 교훈

비교 대상을 정의할 때 **실제 운영 경로 전체**를 재현해야 한다. 파이프라인의 일부만 떼어 평가하면 그 결과는 시스템에 대한 진술이 아니다.

### 수정

MCP arm을 2단계로 만들었다. 도구 실행 후 **같은 모델에 같은 지시문 + 조회 결과**를 주어 답변을 합성한다(`buildSynthesisPrompt`). 이 수정만으로 MCP 정확도가 22.7% → 77.3%가 됐다.

## 실수 4: 출처 식별자 형식을 확인하지 않았다

### 증상

MCP arm의 출처 검증 가능 비율이 0.0%였다. 실제로는 모든 출처가 유효한데도.

### 원인

`verifySourceIds`를 UUID 정규식으로만 작성했다. 그러나 도구가 반환하는 `sourceId`는 `data_source.source_id`(UUID)가 아니라 `data_source.source_key`(`official:<sha256>` 형식)였다.

### 교훈

**검증 로직을 쓰기 전에 실제 값을 한 번 조회해 봐야 한다.** 스키마에 `source_id`가 있다고 해서 API가 그것을 반환한다는 보장은 없다.

### 수정

UUID와 `source_key` 양쪽을 조회한다. 검증 비율이 0% → 51.5%로 정정됐다.

## 부수적 실수: 대조군을 억압하는 지시문

첫 지시문에 "근거가 되는 자료를 확인할 수 없다면 추측하지 말고 '확인할 수 없습니다'라고 답하십시오"와 "제시한 수치에는 출처를 함께 밝히십시오"를 넣었다. 도구가 없는 vanilla는 이를 "너는 자료가 없으니 전부 거부하라"로 읽고 22문항 중 19문항을 거부했다.

**대조군이 전부 거부하는 비교는 근거 능력이 아니라 프롬프트 민감도를 측정한다.** 심사자가 가장 먼저 공격할 지점이기도 하다.

지시문을 vanilla에 최대한 유리하게(근사치라도 제시하라, 출처를 모른다고 수치를 보류하지 말라) 고쳤다. 그리고 **지시문을 완전히 제거한 맨 프롬프트로 대조 실험**을 수행해, 남은 거부가 지시문 탓이 아니라 모델의 실제 행동임을 확인했다.

```
$ (지시문 없이) "2024년 경상북도 구미시의 주민등록 인구는 몇 명입니까?"
→ "...정확한 수치는 제공할 수 없습니다. 최신 통계는 구미시청이나 통계청의 공식 자료를..."
```

이 대조 실험을 하지 않았다면 "우리가 baseline을 일부러 약하게 만든 것 아니냐"는 반론에 답할 수 없었다.

## 종합 교훈

1. **자기 시스템에 유리한 결과가 나오면 채점을 의심하고, 불리한 결과가 나와도 채점을 의심하라.** 이번엔 불리한 결과(MCP 환각률 63.6%)가 버그의 단서였다.
2. **요약 수치만 보지 말고 원시 응답을 열어라.** 네 가지 실수 전부 `report.json`의 응답 텍스트를 직접 읽어서 발견했다. 집계만 봤다면 하나도 못 찾았다.
3. **긴 숫자열이 섞인 텍스트를 수치 채점에 넣지 마라.**
4. **검증 로직 작성 전에 실제 데이터를 한 번 조회하라.**
5. **비교 실험의 대조군에도 최선의 조건을 줘라.** 그리고 그 조건이 최선이었음을 별도 실험으로 입증하라.
