# Vanilla vs MCP 벤치마크 — 경상북도 컨텍스트

일반 LLM(vanilla)과 경상북도 데이터 계층에 연결된 LLM(MCP)이 **같은 질문에 대해 무엇을 다르게 답하는지** 측정한다.

이 벤치마크가 답하려는 질문은 하나다. **"그냥 ChatGPT에 물어보면 되는 것 아닌가?"**

---

## 1. 왜 별도의 벤치마크가 필요한가

기존 `evals/`는 플래너가 카탈로그 정의대로 도구를 고르는지 검증한다. 전 항목 100% 통과이며, 그럴 수밖에 없다. **자기 카탈로그를 기준으로 자기 플래너를 채점**하기 때문이다. 내부 정합성은 증명하지만 "이 시스템이 없을 때와 비교해 무엇이 나아지는가"는 전혀 증명하지 못한다.

이 벤치마크는 그 빈칸을 채운다. 비교 대상은 **동일 모델**이고, 유일한 변수는 **데이터 계층 접근 여부**다.

## 2. 설계 원칙

| 원칙 | 구현 |
| --- | --- |
| 동일 조건 | 두 arm이 같은 모델(`chatClientFromEnv()`), 같은 지시문(`SHARED_INSTRUCTION`), 같은 질문을 같은 순서로 받는다 |
| 객관적 정답 | 정답을 하드코딩하지 않고 **실행 시점에 PostgreSQL에서 조회**한다 |
| 결정론적 채점 | LLM 심판을 쓰지 않는다. 수치 비교·부재 판정·출처 조회 모두 코드로 판정한다 |
| 자기 검증 | 문항의 전제(예: "이 자료는 없다")가 현재 DB와 어긋나면 **실행을 중단**한다 |
| 불리한 문항 포함 | vanilla가 이길 수 있는 대조군을 일부러 넣는다 |

마지막 항목이 중요하다. MCP가 전승하도록 문항을 고르면 그것은 측정이 아니라 홍보다. `common_knowledge` 범주는 일반 모델도 아는 광역 통계로 구성했고, 실제로 vanilla가 득점한다.

### 왜 LLM 심판을 쓰지 않는가

자기 시스템을 자기가 만든 심판으로 평가하면 결과의 설득력이 사라진다. 이 벤치마크의 모든 판정은 다음 세 가지 결정론적 연산으로 환원된다.

1. 답변에서 수치를 추출해 DB 정답과 허용 오차 내 비교
2. 답변이 단정했는지 보류했는지 판별
3. 답변이 제시한 출처 식별자를 `data_source` 테이블에 실제로 조회

## 3. 문항 구성 (22문항 / 6범주)

| 범주 | 문항 | 측정 대상 |
| --- | ---: | --- |
| `common_knowledge` | 3 | **대조군.** 일반 모델도 아는 광역 통계. 접지(grounding)가 기존 능력을 훼손하지 않는지 |
| `recency` | 4 | 학습 컷오프 이후(2026년) 자료. 사전지식으로 도달 불가 |
| `hyperlocal` | 4 | 울릉·영양·봉화·영덕 등 소규모 군 단위 |
| `precision` | 6 | 원 단위 지방세 결산액, 보도자료 총건수 등 근사치로는 통과 불가 |
| `abstention` | 3 | **자료가 실제로 없는 질문.** 답하지 않는 것이 정답 |
| `provenance` | 2 | 수치와 함께 검증 가능한 출처 식별자를 요구 |

`abstention` 범주가 이 벤치마크의 핵심이다. 세 문항 모두 전제를 DB로 확인했다.

- `ab-uljin-pop-2015` — 울진군 인구는 2025년부터만 적재돼 있다
- `ab-cheongsong-pop-2024` — 2024년 인구 관측은 일부 지역만 있고 청송군은 없다
- `ab-policy-programs` — `policy_program` 테이블은 0행이다

전제가 깨지면(예: 나중에 울진군 2015년 자료를 적재하면) 실행이 실패하고 문항 갱신을 요구한다.

## 4. 지표

| 지표 | 정의 | 주의 |
| --- | --- | --- |
| 정확도 | 허용 오차 내 정답 비율. 부재 문항은 보류가 정답 | |
| 답변 시도율 | 보류하지 않고 단정한 비율 | |
| 환각률 (전체) | 전체 문항 중 사실과 다른 단정을 한 비율 | **단독 해석 금지** |
| 환각률 (답변 대비) | 단정한 답변 중 사실과 다른 비율 | 두 arm을 같은 조건에 놓는 값 |
| 부재 인지 정확도 | 자료 없는 문항을 올바로 보류한 비율 | |
| **출처 검증 가능 비율** | 제시한 출처 중 `data_source`에 실제로 조회되는 비율 | 아래 참조 |
| 응답 지연 중앙값 | | 접지의 비용 |

**환각률은 반드시 답변 시도율과 함께 읽어야 한다.** 모든 질문에 "모르겠습니다"라고 답하는 시스템은 환각률 0%를 기록하지만 아무 쓸모가 없다. 이 벤치마크가 두 지표를 나란히 싣는 이유다.

**출처 검증 가능 비율**은 "귀속(attribution)"과 "출처(provenance)"를 가른다. "행정안전부 주민등록 인구통계에 따르면"은 기관 이름을 댄 것이지 확인할 수 있는 지점을 가리킨 것이 아니다. MCP arm이 제시하는 `source_id`는 `data_source` 행으로 조회되고, 그 행은 파일 경로와 SHA-256까지 갖고 있다. 이 지표는 그 차이를 숫자로 만든다.

## 5. 실행

```bash
# 정답 해석과 문항 전제만 검증 (API 호출 없음)
pnpm benchmark:compare:dry-run

# 전체 비교 실행
pnpm benchmark:compare

# 일부만
pnpm --filter @gb/benchmark compare -- --limit 5
```

필요 환경변수: `DATABASE_URL`, 그리고 `OPENAI_API_KEY` / `GROK_API_KEY` / `GEMINI_API_KEY` 중 하나.

산출물은 `benchmark/reports/`에 `report.md`(사람용)와 `report.json`(원시 응답·정답·판정 전체 포함)로 떨어진다.

| 옵션 | 설명 |
| --- | --- |
| `--dry-run` | 정답 해석과 전제 검증까지만 수행 |
| `--limit N` | 앞에서 N문항만 |
| `--cases <경로>` | 다른 문항 파일 사용 |
| `--out <경로>` | 리포트 출력 위치 |
| `--planner heuristic` | MCP arm의 플래너를 결정론적 플래너로 고정 |

## 6. 결과 (gpt-4o-mini, 22문항)

| 지표 | vanilla | MCP |
| --- | ---: | ---: |
| 정확도 | 18.2% | **77.3%** |
| 답변 시도율 | 18.2% | 72.7% |
| 환각률 (전체) | 9.1% | 9.1% |
| 환각률 (답변 대비) | 50.0% | **12.5%** |
| 부재 인지 정확도 | 66.7% | **100.0%** |
| 출처 검증 가능 비율 | 0.0% | **51.5%** |
| 응답 지연 중앙값 | 668ms | 2,546ms |

범주별로 보면 성격이 분명해진다.

| 범주 | vanilla | MCP |
| --- | ---: | ---: |
| 일반 상식 (대조군) | 33.3% | 66.7% |
| 최신성 | 0.0% | 75.0% |
| 지역 밀착 | 0.0% | 100.0% |
| 정밀도 | 0.0% | 50.0% |
| 부재 인지 | 66.7% | 100.0% |
| 출처 검증 | 50.0% | 100.0% |

### 무엇이 실제로 드러났는가

**vanilla의 지배적 실패는 환각이 아니라 침묵이다.** 22문항 중 18문항에서 "확인할 수 없습니다"로 답했다. 이는 지시문 탓이 아니다. 지시문을 완전히 제거한 맨 프롬프트로도 동일하게 거부한다.

```
$ (지시문 없이) "2024년 경상북도 구미시의 주민등록 인구는 몇 명입니까?"
→ "2024년 경상북도 구미시의 주민등록 인구에 대한 정확한 수치는 제공할 수 없습니다.
   최신 통계는 구미시청이나 통계청의 공식 자료를 참고하시기 바랍니다."
```

따라서 이 데이터 계층의 가치는 "환각을 막는다"보다 **"답할 수 없던 질문을 답할 수 있게 만들고, 그 답에 검증 가능한 출처를 붙인다"**로 서술하는 편이 정확하다. 그리고 답을 하는 순간에는 vanilla의 환각률이 50%로 뛴다(`ab-uljin-pop-2015`에서 "약 4만 5천 명"을 지어냈다).

## 7. 이 벤치마크가 찾아낸 우리 시스템의 결함

MCP arm이 틀린 문항은 모두 실제 결함을 가리킨다. 벤치마크의 산출물은 점수가 아니라 이 목록이다.

| 문항 | 증상 | 진단 |
| --- | --- | --- |
| `ck-gyeongbuk-pop-2024` | 광역(경상북도) 인구를 물었는데 포항시 값(499,352)을 반환 | 광역 단위 지역 해석 실패. `extractEntities`가 도(道) 자체를 지역으로 잡지 못한다 |
| `pr-gyeongsan-tax-burden-2024` | '신고 총 세부담액'을 물었는데 '수납액'을 반환 | `get_local_tax_revenue_trend`가 `amount_semantics`를 인자로 노출하지 않아 두 정의를 구분할 수 없다 |
| `pr-press-count-2025` | 총 2,770건인데 "총 5건"이라 답변 | `search_press_releases`의 top-N 결과 개수를 전체 건수로 오인. **집계 도구가 없다** |
| `pr-council-seats-ppp` | 정당별 의원 수를 못 셈 | 의원 명부에 대한 집계 도구 부재 |
| `rc-bill-count-2026` | 연도별 의안 건수를 못 셈 | 의안에 대한 집계 도구 부재 |

즉 가장 큰 단일 개선 과제는 **집계(count/sum/group-by) 도구의 부재**이며, 그 다음이 **광역 단위 지역 해석**과 **지표 정의(semantics) 선택 인자**다.

## 8. 한계

- **실행 간 변동.** LLM은 비결정론적이라 반복 실행 시 범주별 수치가 흔들린다(특히 문항 수가 3~4개인 범주). 결론에 인용할 때는 여러 번 실행해 확인해야 한다.
- **모델 1종.** 현재 `gpt-4o-mini` 기준이다. 더 큰 모델은 사전지식이 많아 vanilla 점수가 오를 수 있다.
- **표본 22문항.** 방향성을 보기엔 충분하지만 소수점 단위 비교에는 부족하다.
- **거부 판별은 어휘 기반.** 두 arm에 동일하게 적용되므로 편향은 없으나 완벽하지 않다.
- **지연 시간 비교는 불리하게 잡혀 있다.** MCP arm은 도구 실행 + 합성까지 2단계를 거치므로 느린 것이 당연하다. 접지의 비용으로 그대로 싣는다.

## 9. 구조

```
benchmark/
├─ cases/gyeongbuk.jsonl     문항 + 정답 명세(값이 아니라 조회 방법)
├─ reports/                  산출물 (report.md / report.json)
└─ src/
   ├─ types.ts               공통 타입
   ├─ cases.ts               문항 로딩·검증
   ├─ ground-truth.ts        DB에서 정답 조회, 출처 식별자 실재 확인
   ├─ korean-number.ts       한국어 수치 파서 ("49만 9839명" → 499839)
   ├─ grade.ts               결정론적 채점
   ├─ report.ts              Markdown 렌더
   ├─ run.ts                 CLI
   └─ arms/
      ├─ prompt.ts           두 arm 공용 지시문
      ├─ vanilla.ts          모델 단독
      └─ mcp.ts              에이전트 도구 실행 + 결과 합성
```

### 한국어 수치 파서가 필요한 이유

접지된 답변은 "132,550명"이라 쓰고, 접지되지 않은 답변은 "약 13만 2천 명"이라 쓴다. 둘 다 같은 사실을 말하려는 시도다. 한쪽 표기만 이해하는 채점기는 정확도가 아니라 문체를 측정하게 된다.

### MCP arm이 2단계인 이유

실제 MCP 클라이언트는 도구 호출에서 멈추지 않는다. 조회된 행을 모델에 되돌려주고 모델이 답변을 작성한다. 1단계(도구 실행)만 평가하면 *모델*과 *데이터 덤프*를 비교하게 되어 접지의 효과를 과소평가한다. 그래서 MCP arm은 도구 실행 후 **같은 모델에 같은 지시문 + 조회 결과**를 주어 답변을 합성한다.
