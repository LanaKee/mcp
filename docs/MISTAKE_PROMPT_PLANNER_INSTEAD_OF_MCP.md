# MCP 서버를 만들어 놓고 MCP로 부르지 않은 실수

## 무슨 일이 있었나

경상북도 공공데이터 MCP 서버를 만들고, 그 위에 웹 프로토타입을 붙였다. 프로토타입은 "MCP 에이전트에 연결됨"이라고 화면에 표시했다. 그런데 실제 경로에 **MCP 프로토콜이 없었다.**

우리가 만든 것은 이랬다.

```
프로토타입 → POST /api/agent → 카탈로그 검색 → 후보를 프롬프트 글로 작성
          → 모델에게 "이 중에서 골라" → 돌아온 JSON 파싱 → 우리가 도구 호출
```

도구를 부를 줄 아는 모델에게 **도구를 설명한 글**을 읽히고 있었다. MCP는 정확히 이 번역 계층을 없애려고 있는 프로토콜인데, 우리가 그 계층을 손으로 다시 지은 것이다.

사용자가 물었다. "왜 MCP가 아니라 prompt로 질의하는가? OpenAI 라이브러리는 MCP를 지원하는데?"

## 왜 알아채지 못했나

**증상이 다른 곳에서 나타났기 때문이다.**

"34세인데 경북에서 스마트팜 창업을 하려면?" 질문이 `plan=0`, `answered=false`로 실패했다. 데이터는 전부 있었다(스마트팜 보도자료 324건, 임대형 스마트팜 34건, 혁신밸리 64건). 검색을 시도조차 하지 않았다.

이것을 **라우팅 버그**로 진단했다. 그리고 실제로 라우팅 버그였다. 근본 원인을 3단계까지 추적했다.

1. `press_release`의 keywords가 형식어(보도자료·발표·도정)뿐이라 주제어가 게이트를 통과하지 못한다
2. 완화해도 `lexicalSearch`가 카탈로그 **설명문**을 랭킹해 조사 "에서"에 걸린 엉뚱한 데이터셋이 상위에 온다
3. 플래너가 단계를 세워 놓고도 `unanswerable`을 선언해 근거가 버려진다

세 군데를 다 고쳤고, 질문은 답을 냈다. 고친 것 자체는 옳았다(각각 회귀 테스트로 고정했다).

**그러나 이 세 가지는 모두 "우리가 지은 번역 계층"의 결함이었다.** 어휘 게이트도, 프롬프트 플래너도, 계획-실행 분리도 MCP 클라이언트를 쓰면 애초에 존재하지 않는다. 층 안에서 버그를 잡느라 그 층이 왜 있는지를 묻지 않았다.

교훈은 "라우팅을 고치지 말았어야 했다"가 아니다. **한 기능에서 서로 다른 원인의 버그가 세 개나 나오면, 그 기능이 있어야 하는지를 먼저 물어야 한다.**

## 무엇이 확인을 늦췄나

전환을 결정한 뒤에도 검증이 한 번 헛돌았다. OpenAI Responses API의 원격 MCP 지원을 시험하는 스크립트가 401을 뱉었다.

```
Incorrect API key provided: "sk-proj****...qcA"
```

세 공급자 키를 전부 시험했더니 셋 다 실패했다. "키가 모두 만료됐다"고 결론 내리려던 참에, **같은 `.env`를 읽는 실행 중인 서버는 멀쩡히 동작하고 있다**는 사실이 걸렸다.

원인은 `.env` 파싱이었다.

```python
env = dict(l.split('=', 1) for l in open('.env'))   # 값이 "sk-proj-..." 로 따옴표째 들어온다
```

`.env`의 값이 따옴표로 감싸여 있었고, 저장소의 `loadRepoEnv()`는 `.replace(/^["']|["']$/gu, "")`로 그것을 벗기고 있었다. 임시 검증 스크립트만 벗기지 않았다.

**모순이 보이면 그 모순을 먼저 설명해야 한다.** "키가 만료됐다"와 "그 키를 쓰는 서버가 동작한다"는 동시에 참일 수 없다. 이 모순을 붙잡지 않았다면 멀쩡한 자격 증명을 재발급받으러 갔을 것이다.

## 무엇을 바꿨나

`prototype/src/lib/mcp-agent.ts`에서 모델을 MCP 서버에 직접 붙였다. 자세한 내용은 `CHANGES_NATIVE_MCP_TOOL_CALLING.md`에 있다.

결과는 같은 질문에서 도구 호출 0건 → 3건, 카드 0장 → 7장, 출처 0건 → 5건.

## 함께 드러난 것: 화면이 한 거짓말

전환 후 라우트 패널이 이렇게 표시했다.

> 후보 0 · 호출 4 · 근거 4 · 출처 5
> **후보 데이터셋이 없었습니다. 이 질문은 보유 범위 밖입니다.**

같은 줄에서 호출 4건과 출처 5건을 세어 놓고 범위 밖이라고 말했다. 그 문구는 카탈로그 게이트가 전부 막았을 때를 위해 쓴 것인데, 네이티브 MCP에서는 모델이 `search_datasets`를 건너뛴 것뿐이다.

**빈 목록을 하나의 의미로만 읽은 것이 실수였다.** 후보 0은 "없다"일 수도 있고 "찾아보지 않았다"일 수도 있다. 파이프라인이 바뀌면 같은 빈 값의 뜻이 바뀐다. 이제는 실행된 호출이 있는지로 둘을 구분한다.

이 프로젝트에서 근거 없는 문장을 내보내는 것이 가장 큰 실패라고 계속 말해 왔는데, 정작 **근거가 있는데 없다고 말하는** 반대 방향의 거짓말을 화면에 넣어 두고 있었다.

## 규칙으로 남기는 것

1. 프로토콜을 쓴다고 말하기 전에 그 프로토콜이 실제 호출 경로에 있는지 확인한다
2. 한 기능에서 원인이 다른 버그가 연달아 나오면, 버그가 아니라 그 기능의 존재를 의심한다
3. 검증 스크립트가 운영 코드와 다른 방식으로 설정을 읽으면, 그 차이가 다음 오진의 원인이 된다
4. 모순되는 두 관측이 있으면 둘 중 하나를 버리기 전에 모순 자체를 설명한다
5. 빈 목록에 문구를 붙일 때는 "없다"와 "보지 않았다"를 구분한다
