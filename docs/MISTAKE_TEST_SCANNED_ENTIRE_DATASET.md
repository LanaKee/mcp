# 실수: 테스트가 데이터셋 전체를 스캔했다

## 증상

경상북도의회 CSV 3개(약 1.7 MB)를 `datasets/`에 추가한 뒤
`pipelines/src/pdf-golden.test.ts`가 120초 타임아웃으로 실패하기 시작했다.
새로 추가한 코드는 이 테스트와 아무 관련이 없었다.

## 오진

처음에는 백그라운드로 돌던 크롤러가 CPU를 먹어서라고 생각했다. 크롤이 끝난 뒤
단독 실행해도 실패했다. 다음으로 커밋되지 않은 변경이 원인일까 싶어 `git stash`
했는데 stash할 것이 없었다. 두 번의 추측 모두 틀렸고, 그제서야 단계별 시간을
측정했다.

```
buildCatalog   132초 (972개 항목)
fixture 로드     2ms
PDF 정규화        1초
```

## 진짜 원인

`buildCatalog()`는 `datasets/` 아래 **모든 파일을 읽어 SHA-256을 계산**한다.
이것은 ETL의 콘텐츠 주소 지정을 위해 필요한 동작이다. 문제는 golden page
테스트가 PDF 6개만 필요한데도 972개 전부를 해싱했다는 것이다.

이 테스트는 원래도 아슬아슬했다. 데이터셋이 커질 때마다 조금씩 느려지다가
council CSV가 임계점을 넘겼을 뿐이다. **council 커밋은 방아쇠였지 원인이
아니었다.**

첫 수정으로 `collectEtlData` 대신 `buildCatalog`를 직접 호출했지만 효과가
없었다. 비용이 카탈로그 작성 자체에 있다는 사실만 확인했다.

## 수정

`buildCatalog(datasetDirectory, repositoryRoot, includePath?)`에 선택적 경로
필터를 추가하고, 테스트가 자신이 쓰는 6개 PDF만 지정하게 했다.

```
130초 → 0.9초
```

## 교훈

1. **성능 회귀를 추측으로 진단하지 않는다.** 두 번의 추측이 모두 틀렸고, 측정은
   한 번에 답을 줬다. 단계별 타이밍을 먼저 찍는다.
2. **테스트가 필요 이상의 입력을 읽으면 데이터가 커질수록 반드시 터진다.** 무관한
   커밋이 무관한 테스트를 깨는 방식으로 나타나므로 원인 추적이 어렵다.
3. `buildCatalog`는 무제한 `Promise.all`로 전 파일을 동시 로드한다. 아직
   메모리 문제는 없지만 데이터셋이 더 커지면 다음 병목이 될 지점이다. 부분
   집합만 필요한 호출자는 반드시 `includePath`를 넘긴다.
