# 넘길 곳을 만들지 않고 넘기라고만 했다

## 증상

8787이 옛 정적 데모 대신 프로토타입을 보여주도록 리버스 프록시를 붙였다.
로컬에서는 완벽하게 돌았다 — 화면, 자산, `/mcp`, SSE 스트리밍까지 전부 실측했다.
그런데 원격에 배포하니 화면이 나오지 않았다.

```
gyeongbuk-public-ai HTTP server listening on http://127.0.0.1:8787 (postgres)
{"error":"http_request_failed","code":"ECONNREFUSED"}
{"error":"http_request_failed","code":"ECONNREFUSED"}
...
```

## 무엇이 잘못됐나

프록시는 정확히 동작했다. 문제는 **넘길 곳이 없었다**는 것이다.

`pnpm start`는 MCP 서버 하나만 띄운다. 프로토타입은 별개의 Next.js 프로세스이고,
그것을 띄우는 일은 내가 로컬에서 **손으로** 하고 있었다. 터미널 두 개를 열어
한쪽에 `pnpm --filter @gb/prototype dev`, 다른 쪽에 서버를 띄웠고, 그 상태에서
"됐다"고 판정했다.

배포된 서버에는 터미널을 두 개 여는 사람이 없다. 그래서 8787은 아무도 없는
3100으로 요청을 계속 넘겼다.

## 진짜 실수

**검증 환경이 배포 환경을 대신할 수 없다는 것을 알면서도, 검증 절차에는
그 차이가 들어 있지 않았다.**

"화면과 서버를 함께 띄워야 한다"는 것을 나는 알고 있었다. README에도 두 줄로
적었다.

```bash
pnpm --filter @gb/prototype dev                     # 3100
PROTOTYPE_ORIGIN=http://127.0.0.1:3100 pnpm start   # 8787
```

적어 두는 것과 **일어나게 만드는 것**은 다르다. 실행 절차를 문서에 옮기는
순간, 나는 그것을 사람이 매번 정확히 재현할 일로 떠넘겼다. 배포 파이프라인은
문서를 읽지 않는다.

같은 구멍이 Dockerfile에도 그대로 있었다. `apps/web` 복사를 지웠지만 그 자리에
프로토타입을 넣지 않았다. 이미지에는 8787이 넘길 대상이 아예 없었다.

## 어떻게 고쳤나

실행 절차를 문장에서 코드로 옮겼다.

- `scripts/serve.mjs` — `pnpm start`/`pnpm dev`가 화면과 서버를 함께 띄운다.
  화면이 연결을 받을 때까지 기다린 뒤에야 서버를 올리고, `PROTOTYPE_ORIGIN`을
  자식에게 직접 넣는다. 사람이 두 값을 맞출 일이 없다.
- `Dockerfile` — 프로토타입을 `output: "standalone"`으로 빌드해 이미지에 넣고,
  `docker-entrypoint.sh`가 두 프로세스를 띄운다.
- `docker-compose.yml` — 화면이 답을 만드는 데 필요한 값(`OPENAI_API_KEY`,
  `MCP_SERVER_URL`, `MCP_BASE_URL`, `MCP_AUTH_TOKEN`)을 컨테이너에 전달한다.

화면 없이 서버만 띄우려면 `SKIP_PROTOTYPE=1`. 이때 화면 경로는 404다.

## 딸려 나온 두 번째 실수: 래퍼만 죽였다

수명을 묶고 나서 확인해 보니 절반만 동작했다. 화면을 죽였는데 8787이 그대로
살아 있었다.

`spawn`한 것은 `pnpm`이고, 실제 서버는 그 **손자**다. `child.kill("SIGTERM")`은
래퍼에만 닿고, 손자는 포트를 쥔 채 고아가 된다.

```
[serve] prototype exited (code=0 signal=null)
--- 8787 살아있나 ---
1722          ← 죽었어야 했다
```

`detached: true`로 자식을 프로세스 그룹 리더로 띄우고 `process.kill(-pid)`로
그룹 전체에 보내도록 고쳤다. 컨테이너 쪽 `docker-entrypoint.sh`는 `pnpm`을
거치지 않고 `node`를 직접 띄우므로 이 문제가 없다.

이것도 "고쳤다"고 선언하기 전에 실제로 죽여 봤기 때문에 발견했다. 코드를
읽는 것만으로는 `kill`이 어디까지 닿는지 알 수 없다.

## 다음에 다르게 할 것

- 실행에 두 프로세스가 필요하면, 그 사실은 문서가 아니라 **엔트리포인트**에
  적는다. 문서는 왜 그런지를 적는 자리다.
- 배포 산출물(이미지, `pnpm start`)에서 한 번은 돌려 본다. 개발 셸에서만
  확인한 것은 "내 터미널에서 된다"까지만 증명한다.
- 프로세스를 내리는 코드는 반드시 **실제로 내려 보고** 포트가 비는지 확인한다.
