# 실수: 데이터 적재량을 테스트에 고정값으로 박아둔 것

## 증상

원격 DB를 대상으로 전체 테스트를 돌렸을 때 다음이 실패했다.

```
FAIL services/mcp-server/src/postgres-repository.integration.test.ts
  > has the measured official population and tax region-year overlap
- { "region_years": 8,  "regions": 4 }
+ { "region_years": 16, "regions": 5 }
```

## 원인

이 테스트는 "공식 인구 × 공식 headline 지방세"의 중첩 개수를 **스냅샷 상수**로
단언하고 있었다.

```ts
expect(result.rows[0]).toEqual({ region_years: 8, regions: 4 });
```

그런데 그 사이 intake 파이프라인으로 봉화군 2017~2024 자료가 추가 적재되면서
중첩이 16개 지역-연도/5개 지역으로 늘었다.

즉 **파이프라인이 의도한 대로 동작해서 테스트가 깨졌다.** 데이터를 더 모으는 것이
이 프로젝트의 목적인데, 테스트는 데이터가 늘지 않는다는 가정 위에 서 있었다.

## 잘못 판단할 뻔한 지점

보도자료 기능 작업 중에 이 실패를 만났기 때문에 처음에는 내 변경이 원인인지
확인해야 했다. `git worktree`로 변경 이전 커밋(`790ea2c`)을 꺼내 같은 테스트를
돌려 **동일하게 실패**하는 것을 확인하고서야 무관한 선행 결함이라고 결론지었다.

교훈: 실패가 내 변경 때문인지 아닌지를 "코드를 읽어서" 판단하지 말고, 변경 이전
리비전에서 재현시켜 확인한다.

## 수정

개수를 갱신하는 것만으로는 같은 문제가 다음 적재 때 재발한다. 그래서 단언 자체를
**불변식**으로 바꿨다.

- 중첩이 비어 있지 않다
- 중첩의 모든 (지역, 연도)가 인구 테이블과 지방세 테이블 양쪽에 실제로 존재한다
- 최소 한 지역은 연속된 두 해를 가진다 (비교 추세 도구가 성립하려면 필요)

같은 파일의 storage capacity 테스트가 이미 같은 이유로
"assert the report agrees with the database rather than pinning a snapshot count"
방식을 쓰고 있었다. 그 판단을 이 테스트에도 적용했다.

README의 coverage 수치는 사실 기술이므로 실측값(16개 지역-연도/5개 지역)으로
갱신하고, 늘어날 수 있는 값임을 명시했다.

## 재발 방지

- 환경 데이터의 **양**은 단언하지 않는다. 데이터의 **관계와 정합성**을 단언한다.
- 문서에 적는 coverage 수치에는 "적재하면 늘어난다"는 성질을 함께 적는다.
- 수치 자체가 회귀 감시 대상이라면 테스트가 아니라 별도 리포트로 다룬다.
