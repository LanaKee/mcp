# 데이터셋 시맨틱 카탈로그 (search_datasets / describe_dataset)

## 배경

기존 도구 10개는 각각 하나의 질문 형태만 답한다. 안전하지만, 호출하는 쪽이
**이미** 다음을 알고 있어야 한다는 전제가 있었다.

- 어떤 데이터셋이 이 질문에 답할 수 있는가
- 그 값의 단위와 의미는 무엇인가
- 어떤 연도·지역이 실제로 적재되어 있는가
- 두 데이터셋을 합쳐도 되는가, 합친다면 무슨 전제가 필요한가

이 지식이 전부 프롬프트나 사람 머릿속에 있으면 AI는 도구를 "고르는" 것이
아니라 미리 정해진 분기를 따라갈 뿐이다. 이번 변경은 그 지식을 **데이터로
표현해서 AI가 스스로 발견**하게 만든다.

## 변경 사항

### `packages/domain/src/catalog.ts` (신규)

데이터셋 7종의 시맨틱 정의. 각 정의는 다음을 담는다.

| 필드 | 의미 |
| --- | --- |
| `grain` | 한 행이 무엇으로 식별되는가 (region_year 등) |
| `evidenceRole` | `observed_fact` 인가 `narrative_context_only` 인가 |
| `measures` | 이름·라벨·**단위**·**정확한 의미**·**비교 시 주의사항** |
| `dimensions` | 각 차원과 그것이 **조인 키인지 여부** |
| `keywords` | 이 데이터셋을 가리키는 큐레이션된 어휘 |
| `tools` | 이 데이터셋을 읽는 MCP 도구와 필수 인자 |
| `usageRules` | 답변에 쓸 때 지켜야 할 규칙 |

`DATASET_RELATIONSHIPS`는 데이터셋 간 조인 그래프다. 각 간선은 **조인 키**,
**왜 합치는지**, **어떤 전제가 깨지면 안 되는지**를 명시한다.

> 선언되지 않은 조합은 "주의해서 조인"이 아니라 **조인 불가**로 취급한다.
> 검토되지 않은 조인을 허용하면 근거 없는 상관관계 주장이 나온다.

### 커버리지는 하드코딩하지 않는다

카탈로그에는 연도 범위·행 수·지역 수를 **적지 않았다**. 이 값들은 질의 시점에
DB에서 직접 측정한다(`getDatasetCoverage`). 손으로 적어둔 커버리지는 시간이
지나면 틀리고, 그것은 이 프로젝트가 다른 모든 곳에서 금지하는 **출처 없는
주장**과 같기 때문이다.

Postgres 구현은 데이터셋마다 별도 쿼리를 쓰지 않고 `DATASET_COVERAGE_PROBES`
선언에서 동일한 집계 형태의 SQL을 생성한다. 손으로 쓴 7개 쿼리는 서로 미묘하게
달라져 비교 불가능한 커버리지 숫자를 조용히 만들어낸다.

### 새 MCP 도구

- **`search_datasets(query, joinableWith?, evidenceRole?, limit?)`**
  질문에 답할 수 있는 데이터셋 후보를 순위와 함께 반환. 각 후보에 실측 커버리지,
  측정 단위, 조인 키, 호출할 도구와 필수 인자가 붙는다.
  - `joinableWith`: 특정 데이터셋과 **선언된 조인 관계가 있는** 것만 남긴다.
  - `evidenceRole: "observed_fact"`: 보도자료·회의록 같은 서술 자료를 제외한다.
- **`describe_dataset(datasetId, includeCoverage?)`**
  데이터셋 하나의 전체 프로필. 측정 항목의 의미와 비교 주의사항, 조인 가능한
  상대와 그 전제 조건, 현재 커버리지를 포함한다.

두 도구 모두 응답의 `limitations` 첫 줄에 **"이 응답은 데이터셋 메타데이터이며
그 자체로 근거가 아니다"**를 넣는다. 카탈로그 조회가 증거로 둔갑하면 안 된다.

## 발견한 결함과 수정: 어휘 없는 질의의 오탐

처음 구현은 `lexicalSearch` 점수만으로 관련성을 판단했다. 테스트에서
`"zzzz 존재하지않는주제 qqqq"` 같은 무의미한 질의가 **데이터셋 3개를 반환**했다.

원인은 `tokenizeKorean`이 3글자 이상 단어에서 문자 bigram을 생성하기 때문이다.
"존재하지않는주제"의 bigram 중 "주제"가 어떤 데이터셋 **설명문**에 들어 있어
점수가 0을 넘었다.

임의의 상위 후보를 답으로 내주는 것은 이 도구가 막으려는 바로 그 실패다.
그래서 **큐레이션된 어휘 기반 relevance gate**를 랭킹 앞에 두었다.

- `datasetVocabulary()`: 제목·keywords·measure 라벨·dimension 라벨만 사용.
  자유 서술문(description)은 **순위 결정에는 쓰되 관련성 판정에는 쓰지 않는다.**
  설명문에는 "주제", "기준" 같은 흔한 단어가 있어 무관한 질문도 걸린다.
- `isDatasetRelevant()`: 질의의 **온전한 단어**(생성된 bigram이 아니라)가 어휘와
  양방향 부분일치할 때만 통과. 한국어는 교착어라 "인구는"이 "인구"와 절대 같지
  않지만 포함하므로, 양방향 포함 검사가 조사 처리에 필요하다.

결과적으로 어휘가 겹치지 않는 질의는 후보 0개와 함께 "다른 표현으로 다시
시도하라"는 안내를 돌려준다.

## 검증

- `packages/domain/src/catalog.test.ts` (11개) — 카탈로그 정합성. 특히
  **선언된 조인 키가 양쪽 데이터셋에 실제로 `joinKey: true`로 존재하는지** 검사해
  관계 그래프가 정의와 어긋나지 않게 고정했다. 모든 수치 measure에 단위와
  비교 주의사항이 있는지도 강제한다.
- `services/mcp-server/src/catalog-tools.test.ts` (11개) — 라우팅, 실측 커버리지,
  조인 필터, evidenceRole 필터, 무관한 질의 거부, 미적재 데이터셋 구분.
- `services/mcp-server/src/catalog-coverage.integration.test.ts` (5개,
  `TEST_DATABASE_URL` 없으면 self-skip) — **생성된 7개 probe SQL이 실제 스키마에서
  전부 실행되는지** 검증. 타입 체크만으로는 SQL 유효성을 알 수 없다.
- 임시 Postgres 16 인스턴스에 `db/schema.sql`(32 테이블)을 적용하고 시드 데이터로
  통합 테스트 5개 통과 확인.
- 실제 운영 DB에 붙여 HTTP end-to-end 확인:
  - `population_observation` 272행 / 2006–2026 / 23개 시군
  - `local_tax_revenue` 544행 / 2017–2025 / 22개 시군
  - 자연어 질의 7종이 각각 의도한 데이터셋으로 라우팅됨
- 전체 회귀: 209 → **231 passed**, 42 skipped.

## 남은 한계

- 카탈로그 항목은 여전히 손으로 정의한다. 새 데이터셋을 적재하면 정의를 추가해야
  한다. 자동 schema inference는 다음 단계다.
- 관련성 판정은 큐레이션 어휘 기반이라 카탈로그에 없는 표현(동의어, 영문 약어)은
  놓칠 수 있다. 어휘 확장이 곧 재현율 개선이다.
