# 경상북도의회 의원별 의안 검색

## 배경

기존 도구로는 "이 사람 공약이 이거였는데 이행했어?" 같은 질문에 아무 근거도
내놓을 수 없었다. `council_record`(49,708행)는 **포항시의회** 회의록이고,
경상북도 광역의원의 의정활동은 데이터베이스에 전혀 없었다.

경상북도의회 누리집(`council.gb.go.kr`)이 의원별 발의의안을 공개하고 있어,
이를 수집해 의원 ↔ 의안 관계를 정규화하고 MCP 도구로 노출했다.

## 사이트 리버싱 결과

| 대상 | 경로 | 비고 |
| --- | --- | --- |
| 의원 명부 | `/kr/member/name` | 64명 전원 + 프로필 팝업이 한 문서(328 KB)에 포함 |
| 의원별 발의의안 | `/member/bill/contents?search_code=<code>&page=N` | 페이지당 10행 고정 |
| 의안 상세 | `/member/bill/contents?reform=view&uid=<32-hex>&search_code=<code>` | 대표발의/공동발의 구분 |
| robots.txt | `User-agent: * / Allow: /` | 전면 허용 |

- 검색 상태는 인라인 `var st_data = {...}`에 노출되며 `mem_sch`, `bill_sch`,
  `proc_sch`, `sdate`, `edate` 등을 담고 있다. 별도 JSON API는 없고 전부
  서버 렌더링 GET이다.
- `limit` 파라미터는 전달해도 **서버가 무시**한다. 페이지당 10행이 고정이므로
  크롤러는 `page`를 증가시키며 걷는다.
- `search_code`는 의원별 키이며 앞자리가 최초 당선 대수를 나타낸다
  (`12009`는 12대부터, `13640`은 13대부터). 대수 식별자가 아니라 사람 식별자다.
- 의안 상세의 테이블은 **캡션으로 식별**해야 한다. 본회의에 오르지 못한 의안은
  본회의 테이블 자체가 없어 위치 기반 인덱싱이 어긋난다.
- 위원회 심사 테이블 일부는 `<tbody>`가 없다. `<tbody>`만 훑으면 소관위원회가
  통째로 비어 보인다.

## 수집 결과

```
의원          64명 (제13대, 국민의힘 58 / 무소속 3 / 더불어민주당 3)
의안        1,454건 (2006-12-26 ~ 2026-08-14)
발의자 링크 24,178건 (대표발의 1,449 / 공동발의 22,729)
목록 페이지   887회 요청
```

의안 종류는 조례안 1,381건, 결의안 15건, 건의안 5건, 규칙안 2건, 동의안 1건이며
처리결과는 원안가결 1,307건, 수정가결 69건, 폐기 59건, 철회 5건, 부결 3건이다.

발의자 링크 24,178건 중 8,529건만 현 명부의 의원과 연결된다. 나머지는 지난
대수 의원이 공동발의자로 서명한 기록으로, **이름은 보존하되 의원 id는 null**로
둔다. 삭제하면 의안의 발의자 명단이 불완전해지기 때문이다.

## 데이터베이스

마이그레이션 `016_gyeongbuk_council_member_bill.sql`로 세 테이블을 추가했다.
자세한 내용은 `DB_CHANGES_GYEONGBUK_COUNCIL.md` 참고.

핵심 설계는 **대표발의(`lead`)와 공동발의(`co`)를 절대 합치지 않는 것**이다.
동료 의원 의안 12건에 서명한 의원은 12건을 발의한 것이 아니다. 두 역할을
합산하면 의정활동을 심각하게 과대평가하게 되므로 `council_bill_sponsor.role`로
분리하고 도구에서도 필터로 노출한다.

## MCP 도구

`search_member_bills` (도구 수 9 → 10, `expensive` 등급).

```jsonc
{
  "member": "김대진",        // 의원명 (부분일치)
  "query": "산림",           // 의안명 검색어
  "role": "lead",            // lead=대표발의, co=공동발의, any=둘 다
  "party": "국민의힘",
  "committee": "농수산위원회",
  "billKind": "조례안",
  "outcome": "원안가결",
  "dateFrom": "2022-07-01",
  "dateTo": "2026-08-31",
  "limit": 10
}
```

`member`와 `query` 중 하나는 필수다. 둘 다 없으면 의회 전체 의안 기록을
쏟아내면서 마치 질문에 답한 것처럼 보이기 때문에 스키마 수준에서 거부한다.

응답에는 `result.members`로 명부 요약(정당·선거구·대표발의 수·공동발의 수)이
함께 실린다. 동명이인이 조용히 병합되지 않고 두 명으로 드러나게 하기 위해서다.

### 공약 이행 판정을 하지 않는 이유

경상북도의회는 **선거 공약을 공개하지 않는다**. 발의 기록만으로 공약 이행을
판정하면 다음 오류가 발생한다.

1. 공약 원문이 없으므로 매칭 대상 자체가 없다.
2. 발의는 의정활동의 일부일 뿐이다. 예산 심의, 행정사무감사, 5분 자유발언은
   포함되지 않는다.
3. `원안가결`은 의회 통과를 뜻할 뿐 조례가 실제로 집행되었다는 뜻이 아니다.
4. 초선 의원은 재임 기간이 짧아 구조적으로 발의 건수가 적다.

따라서 도구는 `evidence_role: "narrative_context_only"`를 붙이고 위 네 가지를
`limitations`에 명시한 뒤, 판단은 호출자에게 남긴다.

## 사용법

```bash
# 크롤 (약 25분, 요청 간격 350ms)
pnpm gb:council:crawl --accept-terms

# 특정 의원만
pnpm gb:council:crawl --accept-terms --members=12009,13640

# 정규화 + 적재
pnpm etl
pnpm db:load -- --skip-schema
```

크롤 산출물은 `datasets/gyeongbuk-council/`에 저장된다.

| 파일 | 내용 |
| --- | --- |
| `경상북도의회_의원.csv` | 의원 명부 |
| `경상북도의회_의안.csv` | 의안 |
| `경상북도의회_의안발의자.csv` | 의안 ↔ 의원 발의 관계 |
| `gb_council_bills.json` | 재개(resume)용 스냅샷 |
| `gb_council.metadata.json` | robots 상태, 수집 시각, 건수 |

`--no-resume`를 주지 않으면 `gb_council_bills.json`에 이미 있는 의안의 상세
페이지는 다시 받지 않는다.
