# 동적 에이전트: 카탈로그 발견 → 도구 선택 → 결합 → 인용

## 배경

기존 `runRepresentativeDemo(questionId)`는 `questionId`로 분기하는 하드코딩
함수였다. 어떤 도구를 어떤 인자로 부를지가 전부 코드에 박혀 있어, 실제로는
"AI가 도구를 고른다"가 아니라 "미리 정해진 경로를 재생한다"에 가까웠다.

이번 변경은 그 분기를 없애고 **질문 → 데이터셋 발견 → 도구 선택 → 실행 →
근거 결합 → 출처 인용**을 실제로 수행하는 에이전트를 도입한다.

## 설계: 계획은 모델이, 검증·실행·인용은 코드가

핵심 결정은 **LLM에게 계획만 시키고 나머지는 전부 결정론적 코드가 처리**하는
것이다.

```
질문
 └→ search_datasets            (카탈로그가 후보 + 실측 커버리지 반환)
     └→ Planner.plan()         ← 여기만 모델이 관여
         └→ validateStep()     ← 안전 경계. 카탈로그가 허가하지 않으면 거부
             └→ executeTool()  (기존 도구, 기존 신뢰 규칙 그대로)
                 └→ joinability() + 출처 수집 + limitations 전파
```

`validateStep`은 계획의 각 단계를 다음 기준으로 검사한다.

1. 그 `datasetId`가 **이 질문의 후보**였는가
2. 그 `tool`이 카탈로그에서 **해당 데이터셋에 연결된** 도구인가
3. 그 도구가 이 서버에 **실제로 등록**되어 있는가
4. 그 데이터셋에 **적재된 행이 있는가**
5. `requiredArguments`가 **전부 채워졌는가**

하나라도 어긋나면 실행하지 않고 `rejectedSteps`에 사유와 함께 기록한다.
따라서 잘못된 계획의 최대 피해는 **거부**이며, 지어낸 답이 될 수 없다.

프롬프트에는 서버의 전체 도구 목록을 절대 넣지 않는다. 모델은
`search_datasets`가 돌려준 후보만 본다. 그래서 모델이 시도할 수 있는 가장 작은
환각조차 이미 후보 밖이고, 검증기가 그것을 잡는다.

## 두 개의 Planner

| Planner | 언제 | 특징 |
| --- | --- | --- |
| `HeuristicPlanner` | 항상 사용 가능 | 결정론적. 지역·연도·나이를 질문에서 추출해 계획 |
| `LlmPlanner` | API 키가 있을 때 | 카탈로그 후보 안에서 모델이 선택. 실패 시 heuristic으로 fallback |

API 키가 없으면 에이전트는 그대로 동작한다. 모델 의존은 **업그레이드이지
요구사항이 아니다.** 키가 있어도 모델 장애 시 fallback이 같은 카탈로그 출력으로
계획하므로 답변의 출처 보장은 어느 쪽이든 유지된다.

`chatClientFromEnv()`가 `OPENAI_API_KEY` / `GROK_API_KEY` / `GEMINI_API_KEY`
중 설정된 것을 골라 클라이언트를 만든다. `temperature: 0`으로 고정해 벤치마크가
재현 가능하도록 했다.

## 카탈로그 커버리지를 계획에 사용한다

Planner는 도구 기본값에 의존하지 않고 **커버리지가 알려주는 실제 dataStatus를
명시적으로 요청**한다.

도구들은 기본적으로 `official_observed`만 조회한다. 그래서 demo 배포에서는
데이터가 있는데도 아무것도 반환되지 않아 에이전트가 "데이터 없음"이라고 잘못
보고했다. 커버리지가 `demo_sample`만 있다고 알려주면 그것을 명시적으로 요청하고,
응답에는 `demo_sample` 라벨과 그에 따른 limitation이 그대로 붙는다. 구분을
숨기지 않으면서 사실과 다른 "없음" 보고를 없앴다.

연도도 마찬가지다. 질문에 연도가 없으면 임의의 창을 가정하지 않고 **그 데이터셋의
실제 적재 범위**를 쓴다.

## 조인은 선언된 것만

두 개 이상의 데이터셋에서 근거를 모으면 `joinability()`로 카탈로그에 **선언된
관계**가 있는지 확인한다.

- 있으면: 조인 키·근거·주의사항을 답변에 붙이고 caveat을 `limitations`에 전파
- 없으면: "선언된 조인 관계가 없어 각각 따로 보고합니다"를 명시

검토되지 않은 조인을 조용히 수행해 근거 없는 상관관계를 만드는 것을 막는다.

## 새 엔드포인트

`POST /api/agent { "question": "..." }`

응답에는 답변뿐 아니라 **경로 전체**가 담긴다: 고려한 데이터셋과 매칭된 용어,
수립한 계획, 거부된 단계와 사유, 사용한 조인과 그 전제, 출처, limitations.
평가자가 "왜 이 도구를 골랐는가"를 되짚을 수 있어야 하기 때문이다.

rate limit 그룹은 `expensive`로 분류했다. 호출당 카탈로그 조회 + 복수 도구 실행
+ 외부 모델 요청이 발생하므로 도구 하나짜리 예산에 넣으면 안 된다.

## 남은 한계

- 계획은 단일 라운드다. 첫 결과를 보고 다시 계획하는 다단계 추론은 없다.
- `draft_public_document`와 `get_source_context`는 선행 단계의 출력이 있어야
  인자를 만들 수 있어 아직 계획 대상이 아니다.
- 결론 문장은 어떤 데이터셋에서 근거를 모았는지까지만 서술한다. 수치 해석 문장
  생성은 의도적으로 넣지 않았다 — 검증되지 않은 자연어 주장을 만드는 순간
  이 프로젝트의 신뢰 모델이 무너지기 때문이다.
