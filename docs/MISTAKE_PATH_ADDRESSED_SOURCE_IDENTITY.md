# 실수 기록: 소스 정체성을 파일 경로로 잡아 사실이 중복 적재된 문제

## 무엇이 잘못되었나

`officialSourceKey` 가 소스 식별자를 이렇게 만들고 있었다.

```ts
export function officialSourceKey(path: string, fileSha256: string): string {
  return `official:${path.normalize("NFC")}:${fileSha256}`;
}
```

해시가 들어 있으니 안전해 보이지만, **경로가 함께 들어 있는 것이 문제**였다.
같은 바이트라도 경로가 다르면 키가 달라진다.

## 왜 이게 치명적인가

모든 사실 테이블의 자연키가 `UNIQUE (source_id, source_row)` 다.

```
source_key 분기  →  source_id 2개  →  (source_id, source_row) 가 충돌하지 않음
                                    →  같은 사실이 2번 INSERT 됨
```

즉 소스 정체성이 곧 사실 정체성인데, 그 정체성을 "파일이 어디에 놓여 있는가"라는
**저장 위치의 우연한 속성**에 묶어버린 것이다. 중복 방지 제약이 있는데도
제약이 걸리지 않는 형태로 데이터가 늘어나기 때문에, 에러 없이 조용히 오염된다.

## 어떻게 발견했나

신규 데이터 intake 파이프라인을 실제 파일로 E2E 검증하던 중이었다.
intake 는 파일 내용을 보고 카테고리를 판정하므로, 투입한 지방세 CSV 를
`datasets/local-tax/` 로 라우팅했다. 원래 경로와 달라진 것이다.

이후 적재 결과를 확인했더니:

```sql
SELECT region_id, fiscal_year, count(*)
  FROM local_tax_per_capita_burden
 GROUP BY 1,2 HAVING count(*) > 1;
-- 47820 | 2020 | 2
-- 47820 | 2021 | 2
-- 47820 | 2022 | 2
```

`data_source` 에는 `file_sha256` 가 완전히 동일한 행이 서로 다른 `file_path` 로
2건 존재했다. 파이프라인이 만든 버그가 아니라, **파이프라인이 기존 버그를
드러나게 한 것**이었다.

## 교훈

1. **정체성은 내용에서 유도해야 한다.** 경로·파일명·수집 시각처럼 언제든 바뀔 수
   있는 속성을 식별자에 섞으면, 그 속성이 바뀌는 순간 같은 것이 다른 것이 된다.
   intake 저장소는 이미 SHA-256 으로만 중복을 판정하고 있었는데, DB 쪽 규칙이
   그와 어긋나 있었다. **같은 도메인 개념에 두 개의 서로 다른 동일성 기준이
   공존하면 언젠가 반드시 갈라진다.**

2. **UNIQUE 제약이 있다고 중복이 없는 것은 아니다.** 제약은 자신이 덮는 컬럼
   조합만 지킨다. 자연키의 한쪽 축(`source_id`)이 오염 가능하면 제약은 통과하면서
   중복이 쌓인다. 제약을 설계할 때는 "이 컬럼이 잘못된 값을 가질 수 있는가"까지
   봐야 한다.

3. **새 기능 검증이 기존 데이터 무결성을 드러낸다.** 파일 경로를 바꾸는 동작을
   처음 도입했기 때문에 이 버그가 처음 재현되었다. 신규 파이프라인을 실제 데이터로
   끝까지 돌려보지 않았다면 운영 DB 가 조용히 오염될 때까지 몰랐을 것이다.

4. **원격 운영 DB 를 먼저 확인했다.** 로컬에서 재현했다고 바로 대규모 정리
   마이그레이션을 운영에 밀어넣지 않고, 운영 DB 의 중복 SHA 그룹이 0건임을
   먼저 조회해 영향 범위를 확정한 뒤 방어적(멱등) 마이그레이션으로 작성했다.

## 조치

- `officialSourceKey(fileSha256)` 로 변경 — 경로 인자 제거.
- `db/migrations/014_content_addressed_sources.sql` — 기존 중복 소스를 FK 안전
  순서로 정리하고 `source_key` 를 재작성. 중복이 없으면 완전한 no-op.
- 동일 바이트가 두 경로에 있을 때 소스가 1건으로 합쳐지는지 검증하는 회귀 테스트 추가.

자세한 내용은 `docs/DB_CHANGES_CONTENT_ADDRESSED_SOURCES.md` 참고.
