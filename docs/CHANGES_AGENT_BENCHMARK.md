# 에이전트 벤치마크와 지역별 커버리지

## 왜 만들었나

기존 평가는 `evals/questions.jsonl` 5문항이었고, 채점은 "예상한 도구가
실행됐는가"만 확인했다. 그것으로는 이 프로젝트가 실제로 주장하는 것 —
**AI가 올바른 데이터를 찾아서, 올바르게 결합하고, 정직하게 인용하는가** — 이
전혀 측정되지 않는다.

그래서 실제 공식 데이터 기준 15문항 벤치마크와, 에이전트 결과 전체를 채점하는
모듈을 만들었다.

## 무엇을 측정하나

| 지표 | 의미 |
| --- | --- |
| `dataset_discovery` | 카탈로그가 필요한 데이터셋을 후보로 올렸는가 (semantic retrieval recall) |
| `answerability` | 답해야 할 때 답하고, **거부해야 할 때 거부했는가** |
| `tool_selection` | 실제로 실행된 도구가 의도한 도구인가 |
| `argument_selection` | 지역·연도를 옳게 골랐는가 (실행된 **모든** 단계에서) |
| `join_accuracy` | 선언된 조인 관계를 올바른 키로 사용했는가 |
| `join_datasets_executed` | 조인 대상 데이터셋이 실제로 실행됐는가 |
| `citation_integrity` | 모든 근거의 sourceId가 답변의 출처 목록에서 해석되는가 |
| `data_status` | official_observed / demo_sample 구분을 정확히 보고했는가 |
| `unavailable_disclosed` | 후보였지만 **비어 있는** 데이터셋을 밝혔는가 |
| `required_disclosure` | 실제 적재 범위 등 필수 고지를 포함했는가 |
| `no_unsupported_claim` | 근거 없이 수치를 주장하지 않았는가 |
| 응답 시간 | 중앙값 / p95 |
| 절감 시간 | 문항별 수작업 기준 대비 (**통과한 문항만** 인정) |

두 가지 설계 선택이 중요하다.

**거부는 실패가 아니라 성공이다.** 데이터가 없는 질문에 답하는 시스템은 답하지
않는 시스템보다 나쁘다. 그래서 `expectAnswerable: false` 문항은 거부해야 통과한다.

**적용되지 않는 검사는 점수에서 제외한다.** 거부 문항에 `citation_integrity`를
적용하면 정답 동작이 감점된다. `passed: null`로 표시해 분모에서 뺀다.

## 15문항 구성

실제 적재 상태를 먼저 측정하고 그에 맞춰 작성했다.

| 데이터셋 | 행 수 | 연도 | 지역 |
| --- | --- | --- | --- |
| population_observation | 272 | 2006–2026 | 23 |
| local_tax_revenue | 544 | 2017–2025 | 22 |
| press_release | 13,707 | 2020–2026 | 경상북도 |
| council_record | 75,862 | 1970–2031 | 10 |
| council_bill | 1,454 | 2006–2026 | — |
| document_chunk | 27,714 | 2006–2026 | 2 |

의도(intent)는 5종이다: `single_dataset_trend`, `cross_dataset`,
`document_search`, `refusal`, `partial_coverage`.

## 실행

```bash
pnpm benchmark -- --planner heuristic --out evals/report-heuristic.json
pnpm benchmark -- --planner llm       --out evals/report-llm.json
```

**두 플래너를 따로 돌리는 것이 핵심이다.** 하나로 합친 점수는 "카탈로그가 잘못된
데이터셋을 올렸다"와 "모델이 잘못 골랐다"를 구분하지 못한다. 실제로 이 분리가
없었다면 아래 결함들을 모델 변덕으로 오인했을 것이다.

통과율이 100%가 아니면 종료 코드가 0이 아니므로 나중에 파이프라인 게이트로 쓸 수
있다.

## 벤치마크가 찾아낸 실제 결함 6건

벤치마크의 가치는 점수가 아니라 **이것들을 찾아냈다는 것**이다.

### 1. 카탈로그가 지역 합집합 연도 범위를 보고했다

`population_observation`은 전체적으로 2006–2026이지만, 포항시만 201행으로 전 구간을
갖고 있고 울진군은 3행(2025–2026)뿐이다. 합집합 범위를 믿은 플래너는 울진군에
2015–2024를 요청했고 도구는 빈 결과를 냈다.

**수정**: 커버리지가 지역별 측정을 함께 반환한다(`regionCoverage`). 플래너는
요청 구간이 그 범위 밖이면 도구를 부르지 않고 **실제 범위를 밝히며 거부**한다.

> 울진군 시군별 인구 관측은(는) 2025~2026년만 적재되어 있어 요청하신
> 2015~2024년 구간은 답할 수 없습니다.

"데이터 없음"보다 훨씬 유용하다.

### 2. 지역 스코프가 도 단위 자료를 지워버렸다 (1번 수정 중 발생시킨 회귀)

처음에는 지역 조건을 `WHERE`에 넣었다. 그러자 `press_release`(전부 경상북도 태그)가
"청도군" 질문에서 `available: false`가 되어 사라졌다.

**수정**: 지역은 `WHERE`가 아니라 `FILTER` 절을 좁힌다. 한 번의 조회로 배포 전체
현황(이 데이터셋이 여기 있는가)과 지역별 현황(그 지역에 어떤 연도가 있는가)을 모두
얻는다. `available` 판정은 **지역과 무관**하게 유지된다.

연도 범위 검사도 도구 단위로 판단한다. 지역 인자를 받는 도구만 지역 범위에 구속되고,
`search_press_releases`처럼 지역을 받지 않는 도구는 전체 범위를 본다.

### 3. `count(*)::bigint FILTER (...)`는 SQL 구문 오류

FILTER는 집계 함수에 직접 붙는다. 캐스트 뒤에 붙이면 파싱되지 않는다. 이 오류로
모든 지역 질문의 커버리지가 실패해 통과율이 15/15에서 7/15로 떨어졌다.

**수정**: `(count(*) FILTER (WHERE ...))::bigint`.

### 4. 지명만으로 데이터셋이 선택됐다

"경상북도의 국세 납부 실적을 알려줘"가 `press_release`에 매칭됐다. 매칭된 유일한
용어는 **"경상북도"**였다. 국세는 이 프로젝트 범위 밖인데, 시스템은 무관한
보도자료로 출처까지 붙은 답을 만들었다.

**수정**: 이 카탈로그의 모든 데이터셋이 경상북도에 관한 것이므로 **지명은 주제가
아니다.** 지명·행정구역 용어를 관련성 판정에서 제외했다(순위 계산에는 남는다).
`^한글 2~4자+(시|군|읍|면|동)$` 패턴으로 시군 이름도 함께 제외한다.

### 5. 카탈로그가 도구에 거짓 계약을 광고했다

- `search_member_bills`의 `requiredArguments`가 `[]`였지만 스키마는 member 또는
  query 중 하나를 요구한다.
- `search_policies`가 `["region","query"]`였지만 `age`도 필수다.

플래너가 카탈로그를 성실히 따라도 도구가 거부하는 호출이 만들어졌다.

**수정**: 선언을 실제 스키마에 맞췄고, **모든 바인딩의 requiredArguments만으로
도구의 zod 스키마를 통과해야 한다**는 계약 테스트를 추가했다. 이 클래스의 버그가
다시 생기면 테스트가 잡는다.

### 6. 모델이 `query: ""`를 보냈다

인자가 "존재"하지만 `min(1)`을 위반한다. `validateStep`은 undefined/null만 봤다.

**수정**: 안전 경계가 **도구 자신의 파서**로 사전 검증한다. 별도 규칙을 두면
언젠가 어긋나므로, 같은 검증기를 쓴다. 빈 문자열도 누락으로 취급한다.

추가로 `LlmPlanner`는 빈 데이터셋을 겨냥하거나 필수 인자가 비어 있는 단계를 스스로
버리고, 남은 단계가 없으면 결정론적 플래너로 fallback한다. 모델이 피할 수 있었던
거부를 만들어내지 않게 하기 위해서다.

## 결과

| | heuristic | llm:gpt-4o-mini |
| --- | --- | --- |
| 통과 | **15/15 (100%)** | **15/15 (100%)** |
| 응답 중앙값 | 0.13s | 1.93s |
| p95 | 2.64s | 3.35s |
| 수작업 383분 대비 절감 | 382.8분 | 382.5분 |

전 지표 100%. 수정 전 최초 측정은 heuristic 11/15, LLM 12/15였다.

절감 시간은 문항별로 근거를 적어둔 수작업 기준(`manualBaselineRationale`)에서
계산한다. 예를 들어 인구-지방세 교차 질문 45분은 두 출처의 지역명 표기와 회계연도
기준을 사람이 맞춰야 하는 시간이다. **통과한 문항만** 절감으로 인정하므로, 빠르지만
틀린 답은 점수를 얻지 못한다.

## 한계

- 15문항은 회귀 감지용으로는 충분하지만 통계적 일반화에는 부족하다.
- 수작업 기준 분(minute)은 실제 사용자 측정이 아니라 원자료 접근 절차에 근거한
  추정이다. 근거를 문항마다 남긴 이유가 그것이다.
- 100% 통과는 "이 15개 질문에서 회귀가 없다"는 뜻이지 "임의의 질문에 정확하다"는
  뜻이 아니다.
