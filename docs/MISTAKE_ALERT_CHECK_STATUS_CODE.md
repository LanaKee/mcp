# 실수: alert-check.sh가 스토리지 응답 HTTP 상태를 확인하지 않음

## 무엇이 잘못됐나

`scripts/ops/alert-check.sh` 초기 구현은 `/api/admin/storage`를 호출할 때
`curl -s`로 응답 **본문만** 받아 `warnings` 배열을 파싱했고, HTTP 상태 코드는
확인하지 않았다. `curl`은 4xx/5xx에서도 기본적으로 비0 종료 코드를 내지 않으므로
`|| echo '{}'` 폴백은 네트워크 실패에만 반응하고 HTTP 오류에는 반응하지 않았다.

그 결과 토큰이 잘못됐거나(401) 저장소 리포팅이 불가능해(503) 서버가 실제로
문제 응답을 돌려줘도, 그 오류 바디에 `warnings` 키가 없으면 스크립트는 이를
"경고 없음 = 정상"으로 해석해 조용히 통과시켰다. 알림 스크립트가 정확히
알려야 할 장애 상황에서 침묵하는 것은 알림 시스템 자체의 신뢰를 깨는 결함이다.

## 어떻게 발견했나

로컬에서 실제 mcp-server를 띄우고 `ADMIN_TOKEN`을 일부러 틀리게 준 뒤
`alert-check.sh`를 실행했다. `/api/admin/storage`가 401을 반환했음에도
스크립트가 `exit 0`으로 끝나는 것을 확인해 결함을 재현했다.

## 수정

`curl -s -w '\n%{http_code}'`로 본문과 상태 코드를 함께 받아 상태 코드가 200이
아니면 즉시 문제로 기록하고, 200일 때만 본문을 파싱해 `warnings` 배열을 확인하도록
바꿨다. 같은 재현 시나리오(잘못된 토큰 → 401)로 다시 실행해 이번에는 `exit 1`과
webhook 알림 전송을 모두 확인했다.

## 교훈

HTTP를 폴링하는 헬스체크/알림 스크립트는 상태 코드와 본문을 **항상 함께**
검사해야 한다. 본문 스키마만 보고 "필드가 없으니 정상"이라고 판단하면, 애초에
그 스키마를 반환하지 않는 오류 응답(다른 오류 포맷, 빈 바디, 502 HTML 등)을
전부 놓친다.
