# 실수 기록: 파생 키를 추적하지 않고 source_key 를 바꿔 운영 데이터를 잃은 문제

## 요약

`source_key` 를 콘텐츠 주소 방식으로 재작성하는 마이그레이션 014 를 적용하면서,
**`source_key` 로부터 파생되는 다른 키를 확인하지 않았다.**

```ts
// pipelines/src/pdf.ts
const documentKey = `document-${sha256(source.sourceKey).slice(0, 48)}`;
```

`document_key` 가 `source_key` 의 해시였기 때문에, 소스 키를 바꾼 순간 기존 문서
409건이 **주소를 잃었다**. 이후 PDF 파이프라인이 그것들을 "없는 문서"로 판단해
408건을 새로 만들었다.

```
document        409 → 817
document_chunk  65,847 → 90,412
```

## 2차 실수: 복구 방법을 잘못 골랐다

중복을 발견하고 나서, 나는 **"파생 규칙과 맞지 않는 문서를 삭제"** 하도록
마이그레이션을 확장했다. 중복은 사라졌지만 그 대가가 컸다.

```
document_chunk  90,412 → 24,565   (현행 청크는 온전)
stale chunk     41,282 → 0        (보존 정책이 들고 있던 과거 버전 소실)
pdf_processing_version 다중 → 1건
```

삭제된 것은 **이전 추출기/청커 버전이 만든 과거 처리 버전**이었다. 현행 검색
데이터(24,565 청크 / 12,522 페이지)는 온전했지만, 수명주기(lifecycle) 기능이
관리하던 이력은 되살릴 수 없다. 과거 버전은 지금 코드로 재생성할 수 없기 때문이다.

올바른 조치는 삭제가 아니라 **re-key(갱신)** 였다. 소스마다 문서는 하나이므로,
`document_key` 를 새 파생값으로 UPDATE 하면 그래프 전체가 그대로 따라온다.
마이그레이션은 그렇게 수정했고, 로컬에서 무손실·멱등임을 검증했다. 그러나
원격의 이력은 이미 사라진 뒤였다.

## 교훈

1. **식별자를 바꾸기 전에 그 식별자에서 파생되는 모든 것을 먼저 찾는다.**
   `grep "sourceKey"` 한 번이면 `document_key` 파생을 발견할 수 있었다.
   나는 `source_key` 를 *읽어서 경로를 되파싱하는* 코드가 없다는 것만 확인하고
   안전하다고 판단했다. 확인해야 했던 것은 "누가 읽는가"가 아니라
   **"누가 이것으로부터 자기 정체성을 만드는가"** 였다.

2. **키 변경은 데이터 변경이다.** 스키마만 보면 `source_key` 는 텍스트 한 컬럼이다.
   하지만 그 값이 다른 테이블의 주소를 결정하고 있었으므로, 사실상 여러 테이블을
   동시에 재배치하는 작업이었다.

3. **손실 복구는 "지우기"가 아니라 "다시 연결하기"를 먼저 고려한다.**
   중복을 보고 반사적으로 DELETE 를 택했다. 중복의 원인이 "끊어진 연결"이었으므로
   연결을 복원하는 편이 언제나 우선이다. 지우기는 되돌릴 수 없고, 연결 복원은
   되돌릴 수 있다.

4. **운영 DB 에 적용하기 전에 검증 DB 에서 같은 형태의 데이터로 시연했어야 한다.**
   로컬 검증 DB 는 `--skip-pdf` 로 적재해 문서가 0건이었다. 그래서 문서 그래프에
   미치는 영향을 로컬에서는 관측할 수 없었다. **검증 환경이 운영과 다른 축을
   비워두고 있으면, 그 축의 사고는 반드시 운영에서 처음 발생한다.**

5. **테스트가 운영 데이터 스냅샷에 의존하면 사고를 늦게 발견한다.**
   `staleChunks >= 41_282`, `chunks = 17_487` 같은 하드코딩된 기대값은 "쌓여 있는
   쓰레기의 양"을 검증하고 있었다. 이것들은 회귀를 잡아주지 못하고, 환경이 바뀌면
   원인과 무관하게 깨진다. 해당 테스트는 자체 픽스처를 만들거나 DB 실측값과
   비교하도록 고쳤다.

## 조치

- `db/migrations/014_content_addressed_sources.sql` — 문서를 삭제하지 않고 re-key.
  소스당 정본 1건을 남기고 주소 없는 사본만 제거. 멱등.
- `pipelines/src/lifecycle.integration.test.ts` — 롤백 테스트가 운영에 쌓인 과거
  버전을 찾아 쓰던 것을 자체 픽스처 생성으로 교체. 과거 청크 수 기대값 제거.
- `services/mcp-server/src/postgres-repository.integration.test.ts` — stale 청크
  수를 DB 실측과 비교하도록 변경.
- 두 통합 스위트가 청크 가시성을 동시에 건드려 서로를 깨뜨리던 문제를
  PostgreSQL advisory lock 으로 직렬화.

## 남은 손실

원격 DB 의 과거 처리 버전 이력(약 41,282 청크)은 복구 불가하다.
현행 검색 데이터는 전량 온전하며 통합 테스트 171건이 모두 통과한다.
보존 정책은 앞으로 생성되는 새 버전부터 다시 이력을 쌓는다.
